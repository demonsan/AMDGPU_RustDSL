# Compile time: where it goes, how it parallelizes, what ~1 ms per kernel needs

Measured on node 53 (release `amdc`, 2026-11-14; a 64-CPU allocation of the 256-logical-CPU node), in-process: the numbers do not include process start-up. Reproduce with `amdc emit <kernel> --time [--assemble]` and
`amdc compile-batch --jobs N [--time] [--no-verify] [--assemble] [--repeat R]`. The per-phase recorder is `amdgpu_codegen::timing` (per-thread, opt-in by the caller, no environment switch; the pass manager brackets every named pass with it).

## 1. Result in one table (all 240 kernels of the golden manifest, `compile-batch`, verify on, own backend)

| build | 1 thread | 8 threads | note |
|---|--:|--:|---|
| before this work (`485b3000`) | 36.2 s (6.6 kernels/s) | 6.0 s (40/s) | the longest single kernel (5.5 s) bounded the wall time from 8 threads up |
| after the first round (verifier, ladder hints, allocator) | 6.3 s (38/s) | 0.84 s (287/s) | median 1.0 ms, p90 34 ms, max 0.69 s per kernel |
| **after the second round (list scheduler, layout)** | **4.6 s (52/s)** | **0.69 s (347/s)** | median 1.0 ms, p90 29 ms, max 0.59 s |

The assembly is byte-identical: `amdc md5-manifest --check tests/golden/md5_manifest.tsv` reports 240 kernels, 0 differences after every step.

## 2. Phases for a spread of kernels (ms, one compile, after)

`dsl-build` = the kernel builder (`kernel_by_name`); `compile` = lower -> schedule -> allocate -> hazards / waits -> verify -> emit (own tail); `assemble` = the external `clang` (assembler + linker, one process per kernel).

| kernel | dsl-build | compile | assemble (clang) | notes |
|---|--:|--:|--:|---|
| `silu_mul_bf16_d4096` (eltwise) | 0.11 | 0.77 | 26.5 | lower-mir 0.4 |
| `rmsnorm_quant_fp8_n4096` | 1.28 | 4.8 | 33.2 | |
| `gemm_a8w8_rowcol_fp8_64` (small GEMM) | 18.0 | 4.8 | 24.2 | the DSL build (layout / tile algebra) dominates |
| `pa_decode16_bf16_hd128_p16_f` | 0.82 | 13.6 | 30.6 | |
| `mla_decode_bf16_hp_p16` | 0.89 | 52.8 | 31.4 | one retry rung (hinted) |
| `fmha_fwd_hd128_mxfp8_v3_vs128` | 52.0 | 285 | 65.9 | sched-list 103, regalloc 97, lower 34 |
| `fmha_fwd_hd128_fp8pt_v3_causal` | 90.5 | 663 | 76.2 | regalloc and list scheduler |

The external assemble costs 25 - 33 ms for every small kernel: 30 - 40x the whole in-process compile. It is process start + `lld`, not assembly.

## 3. What is needed for a JIT, and what can move offline

| step | needed per JIT compile? | cost (small / large kernel) |
|---|---|---|
| DSL build + lowering + scheduling + allocation + hazards / waits + emit | yes (produces the code) | 0.1 - 5 ms / 0.3 - 0.7 s |
| `verify-gpu` (MIR register / wait legality, `gpu_verify::enforce`) | **no**: a pure check, the output is the same. Cache it per (kernel, shape bucket): `CompileOptions { verify: false }` / `compile-batch --no-verify` skips it | 0.5 ms / 6 - 10 ms now |
| IR-level analyses (values / bounds, tile protocols, stage contracts: `verify_ir`) | no, never in the default mode (strict / `amdc gpu-verify` only) | was 87 % of the compile time of the biggest kernels; no longer run by default |
| assemble to `.co` | yes, until an in-process encoder exists | 25 - 33 ms (clang) |

## 4. What was found and fixed (every step md5-identical; `amdc md5-manifest --check` = 240 kernels, 0 differences)

| hot spot | cause | fix | effect |
|---|---|---|---|
| `verify-gpu` = 48 % of all compile time (2.4 s of 2.9 s for `vs128`, 7.9 s for `fp8pt_v3_causal`) | the default verifier mode computed the whole IR analysis (`verify_ir`) and threw the result away: only the MIR errors reject in the default mode | `gpu_verify::enforce` runs `verify_ir` only for `Warn` / `Strict` | 36.2 s -> 18.9 s (1 thread), `vs128` 2.9 s -> 0.38 s |
| retry ladders: 5 kernels ran the whole schedule + allocation 21 - 49 times (12.8 s of 18.9 s) | the outer / inner ladders retry on `out of VGPRs`; every failed rung repeats the work | `Function::ladder_hint` (first rung that succeeds), table `crates/amdgpu-kernels/src/ladder_hints.rs` (6 kernels), generated by `amdc ladder-hints` (`tools/regen_ladder_hints.sh`), checked by `crates/amdgpu-kernels/tests/ladder_hints.rs` (every hint = the unhinted first-success rung; hinted and unhinted asm identical); specialization clears the hint | 18.9 s -> 7.7 s (1 thread), longest kernel 5.0 s -> 0.94 s |
| `Layout::at` (kernel builders): symbolic `Ix` arithmetic and a `HashMap` per call | | integer fast path for static layouts (`at_flat`), property-tested against the symbolic path (`crates/amdgpu-layout/tests/at_fast_path.rs`) | DSL build -35 % for the layout-heavy kernels |
| `regalloc::precise_segments` (15 % of the big kernels): liveness with `HashSet<Slot>` | | bit-vector sets | 3.0 G -> ~0.5 G instructions |
| `sched::list::schedule` (12 % self time of the big kernels, 1.3 s CPU over the batch) | `HashMap` pressure tracker (SipHash), the cost / read-write / height setup recomputed for each of the six windows, a fresh pool per step | dense `Vec` tracker, `prepare` once per block, reused pool (same picks, same permutation) | 1.3 s -> 0.47 s CPU; `fp8pt_v3_causal` list scheduling 195 -> 63 ms |
| `Layout::at` fast path allocated (`flatten` twice per call: 15 % of the small GEMM's kernel build) | | leaves into fixed arrays, no heap | kernel build 1.2 s -> 0.37 s CPU over the batch (small GEMM 11 -> 2 - 4 ms) |
| `regalloc::check_reaching` (33 % of the big kernels): round-robin fixpoint cloning nested maps, `effects()` recomputed each round, SipHash | | block writes precomputed once, worklist fixpoint (same least fixed point), Fx hasher (`amdgpu-codegen/src/fxhash.rs`; iteration order of std maps is already randomized, so no code depends on it) | regalloc CPU 3.4 s -> 1.7 s over the batch |

## 5. Parallel compile

The compiler is a pure function `Function -> asm`; `std::thread::scope` workers pull kernels from an atomic counter (`amdc compile-batch --jobs N`, `crates/amdc/src/batch.rs`; `amdc md5-manifest --jobs N` already used the same pattern). No shared mutable state besides the per-thread phase recorder.

| jobs | 1 | 2 | 4 | 8 | 16 | 32 | 64 |
|---|--:|--:|--:|--:|--:|--:|--:|
| wall (s), 240 kernels | 6.28 | 3.15 | 1.60 | 0.84 | 0.79 | 0.82 | 0.81 |
| kernels / s | 38 | 76 | 150 | 287 | 303 | 292 | 297 |
| cpu utilization | 100 % | 100 % | 99 % | 97 % | 52 % | 28 % | 17 % |

Scaling is linear to 8 threads; beyond it the wall time is the critical path, i.e. the largest kernel (0.69 s for `fp8pt_v3_causal`), not the thread count. With the external assemble (`--assemble`): 13.2 s (1 thread), 1.57 s (8), 0.94 s (32), 0.98 s (64): clang is 2x the in-process compile CPU, and 64 concurrent clang processes do not scale past the process-spawn rate.

## 6. The in-process assembler (no clang)

`amdgpu_target::gfx950_co` (`crates/amdgpu-target/src/gfx950_co/`, pure safe Rust, no dependencies) turns the compiler's assembly text into the code object `clang -x assembler -mcpu=gfx950 -mcode-object-version=6` + `ld.lld` produce, **byte for byte**:
`enc.rs` encodes instructions (SOP1/2/C/P, SMEM, VOP1/2/C with DPP / SDWA, VOP3 / VOP3P, MFMA / SMFMAC / the 128-bit scale MFMA, DS, MUBUF, global; literals and inline constants; branch offsets), `tables.rs` holds the opcode and
format of every mnemonic (generated by `tools/regen_enc_tables.sh` from the llvm-mc oracle), `co.rs` writes the ELF (lld's layout for one kernel: `.note` with the msgpack AMDGPU metadata, dynamic symbols and both hash tables,
`.text` = code + `s_nop` fill + kernel descriptor, `.dynamic`, `.symtab` in the assembler's first-mention order, section and program headers).

| | clang + lld | in-process |
|---|--:|--:|
| `silu_mul_bf16_d4096` | 26.5 - 37 ms | 0.11 ms |
| `gemm_a8w8_rowcol_fp8_64` | 24 - 33 ms | 0.45 ms |
| `pa_decode16_bf16_hd128_p16_f` | 24 - 31 ms | 1.2 ms |
| `fmha_fwd_hd128_mxfp8_v3_vs128` | 66 ms | 8.2 ms |
| all 240 manifest kernels (CPU) | 7 s | **0.2 s (0.8 ms per kernel)** |

Evidence (clang stays the cross-check and the fallback):
* `amdc co-check /tmp/oracle.tsv`: all 92,635 unique instruction lines of the 240 kernels encode identically to `llvm-mc -show-encoding`;
* `amdc co-verify DIR`: **240 of 240** code objects byte-identical to clang's (`crates/amdc/tests/co_oracle.rs` runs the same comparison for every manifest kernel whenever a clang is found, and the clang-free golden `tests/golden/co_md5_manifest.tsv`, `amdc md5-manifest --co --check`, always);
* hardware smoke: `python/tests/run_all.sh` on node 53 / GPU 1 with the Python JIT on the in-process path (`amdc emit --co`; no clang assembly invocation was made): op checks 62 / 62 PASS, overall PASS.

Use: `amdc emit <kernel> --co FILE.co` (exit 3 and no code object when a kernel uses something the encoder does not know: the Python JIT then falls back to clang; `AMDGPU_JIT_ASSEMBLER=clang` forces clang), `amdc assemble-co FILE.s --out FILE.co`,
`amdc compile-batch --assemble-inproc` (timed), `amdc emit --time` (phase `assemble-inproc`).

## 7. What "~1 ms per kernel" needs

Today (median over the 240 kernels, 1 thread): compile **1.0 ms** + in-process assemble about 0.1 - 1 ms for small kernels; with the DSL build 1.1 ms. What is left for a ~1 ms JIT of a small kernel end to end:

1. ~~In-process encoder instead of clang~~ done (section 6): the 25 - 33 ms floor is gone.
2. **Verification cached offline** per kernel and shape bucket (`CompileOptions { verify: false }`): 0.5 ms of the 0.77 ms for the eltwise kernel and 10 - 40 % of the mid-size ones.
3. **Shape specialization of a pre-lowered IR**: the DSL build (0.1 ms eltwise, 11 - 18 ms for the small GEMM, 90 ms for `fp8pt`) and lowering (0.4 ms, 1.6 ms, 52 ms) do not depend on the shape bucket for the kernels JIT'd per shape: build and lower once per (kernel, parameter set), keep the MIR, and per shape only patch the kernarg-derived constants and re-run the late passes (hazards / waits / emit). Kernels whose scheduling depends on the shape (the FMHA families) keep a per-shape compile of 0.3 - 0.7 s; those are compiled once per model deployment, not per call.
4. **Remaining compile hot spots** (CPU of the 240-kernel batch, 6.5 s): register allocation 1.7 s, list scheduler 1.3 s, DSL build 1.2 s, lowering 0.9 s, ld-ahead 0.24 s: concentrated in the ~20 FMHA / MLA kernels.

Shape buckets: the compile result is a pure function of (kernel, specialization), so an on-disk cache keyed by `compiler_hash` (already in `amdc jit-info`) plus the specialization turns a repeated shape into a file read.

## 8. End to end: a Python `get_kernel` call to a loaded kernel (`tools/jit_bench.py`)

Measured on node 53 / GPU 1 (HIP module load included), release `amdc`, the Python JIT with the in-process assembler; 4 kernels x 32 distinct specializations (the eltwise kernel, `rmsnorm_quant_fp8_n4096`, the small GEMM, `pa_decode16`), "cold" = empty disk cache.
The node is shared, so a single run varies by 30 - 50 %; the table is the **median of 5 runs**.

What the cold path now is (each item was measured; the first two were in `sched-jit`):
* **one process, one compile** (`amdc emit --co --info`; the JIT used to run `emit` and `jit-info`, i.e. compile twice), one lock per cache key, the certificate on its own thread;
* **the certificate** (`certify_specialized`: the IR-level analysis that proves the launch contract for the bound constants) **is never skipped**, but:
  * it no longer compiles the kernel a second time (it was `gpu_verify::analyse` = compile + `verify_ir` + `verify_mir`; now `verify_ir` runs on the thread, `verify_mir` runs on the MIR of the compile that produces the assembly: the verdict is the same set of findings);
  * `gpu_protocol::check_pair` (the tile-protocol pair check, 39 % self time of the small GEMM's certificate) was quadratic in the number of events: the reuse-alias scan now looks only at pairs of events whose tiles are related by a declared reuse, the write-write scan at the producers of one (tile, slot), the consumer scan skips a consumer that an index proves clean (anything else takes the full scan, which reports exactly as before), `is_owner` is evaluated once per event, the simulation's maps use the Fx hasher. **Identical verdicts**: `crates/amdgpu-kernels/tests/gpu_protocol_diff.rs` runs the indexed and the reference (quadratic) pair checks on every manifest kernel and compares the rendered findings; the mutation tests (`gpu_tiles`, `gpu_semantics`) pass. Certificate time: small GEMM 47 -> 18 ms, `pa_decode16` 24 -> 17 -> ~9 ms of `verify_ir` on its own thread, `rmsnorm_quant` 10 -> 7 ms, eltwise 1 ms;
* **a content-addressed certificate cache**: the key is the md5 of the exact specialized IR (`format!("{:?}", Function)`: every field; a test checks the text is deterministic across independent builds and that another shape or kernel gets another key), the cache directory carries the compiler's hash
  (`<jit cache>/certs/<sha256(amdc)[:24]>`, next to the `.co` cache), so a cached verdict is reused only for a byte-identical IR under the same compiler; only passing verdicts are stored, a damaged or foreign entry is recomputed (`tests/jitc.rs`). The MIR-level check always runs (it needs the compile). `amdc certify-batch FILE` (`kernel<TAB>name=v,..` lines) pre-populates the cache offline: 128 shapes in 0.06 s;
* **`amdc serve`**: a persistent compile server (std only; stdin / stdout lines, one worker thread per CPU, the very `compile_request` the CLI runs) that the Python JIT uses by default (`AMDGPU_JIT_SERVER=0` goes back to one process per kernel; any server failure falls back to the CLI).

| configuration (ms per kernel, cold, median of 5 runs) | sequential | 1 worker | 4 workers | 16 workers | 32 workers |
|---|--:|--:|--:|--:|--:|
| one `amdc emit` process per kernel | 15.8 | 14.7 | 3.6 | 1.2 | 1.1 |
| persistent compile server | 15.2 | 17.8 | 4.5 | 1.1 | 0.9 |
| server + certificates pre-populated (`certify-batch`) | **7.3** | 11.0 | 2.4 | 0.9 | **0.8** |

A quiet run of the last row, per kernel (cold sequential, median ms): eltwise 1.2, `rmsnorm_quant` 8.6, small GEMM 8.8, `pa_decode16` 9.3. **Disk-warm** (new process state, populated cache: key + read + `hipModuleLoadData`): **0.5 ms** per kernel (0.3 ms in a quiet run); **memory-warm**: **1.4 us**.

**The honest end-to-end statement:** a cold specialized kernel is **1 - 9 ms** from the Python call to a loaded kernel with the certificates pre-populated (7.3 ms mean over the four kernel classes; the eltwise kernel is at 1.2 ms), about 15 ms when the certificate has to be computed on the spot; a cold batch of 128 shapes over 32 workers is **0.8 ms per kernel** (1.2 k kernels / s). What is left of the cold time is the compile itself (rmsnorm 6 ms, small GEMM 6 ms, decode 9 ms: register allocation, lowering, the schedulers),
which the shape-bucket specialization of a pre-lowered IR (section 7, item 3) would cut; the certificate is off the cold path for pre-certified shapes and runs concurrently with the compile otherwise.
