# Crate split: survey, mapping, problems, merge sequence

Design document for phase P1 of [refactor-4layer-plan.md](refactor-4layer-plan.md) (four layers, downward-only
dependencies: kernels -> L1 -> L2 -> L3 -> L4). Survey of `sched-refactor` at origin/Main `a5fc452d`. Nothing in this
document is implemented; line counts are `ReadAllLines` counts of tracked files (src = `src/**`, tests = `tests/**`).
The dependency graph below was derived from `Cargo.toml` and `use` statements with `git grep` only (no cargo on the
survey machine), so every claim of the form "X does not use Y" means "no `use` / path of Y found in X", not a compiler check.

### 2.5 Decisions needed (mapping)

| # | Question | Recommendation |
|---|---|---|
| D1 | `amdgpu-sym`, `amdgpu-safeasm` are not in the plan | Keep both as foundation crates below L4 (`F`): they have no upward edges. |
| D2 | `contract.rs` (54) and `handoff.rs` (180) are listed as L2 in the plan but are function-level code (they use `Ctx` / `PrivRef` / `ConvPlan`) | Keep both in `amdgpu-tile` (L3); only `contract_stage.rs` is L2. Either placement is downward-legal, so this is cheap to reverse. |
| D3 | `components.rs` is FMHA-flavoured (`gqa_kv_head`, `kv_split_*`), kernels import it from 4 files | Move to `amdgpu-stage` as "grid maps" per plan; if the owner prefers generic-only L2, leave in `amdgpu-tile` and move in the template extraction. |
| D4 | gfx950 atoms (`amdgpu-isa`) embed `Layout` (L3); `amdgpu-target` is L4 | Keep `amdgpu-isa` as the L3 atom crate; `amdgpu-target` holds only scalar / table facts and the atom *set* by name. The alternative (move `amdgpu-layout` below L4) breaks the plan's layer table. |
| D5 | `sched/model.rs`, `op_attrs.rs`, `hazards.rs` tables are keyed by codegen's `MOp` | Either move the `MOp` enum (`mir.rs:99-591`, about 490 lines) to `amdgpu-target` as the instruction set, or keep the tables in a `codegen::target_tables` module that implements the `Target` trait. | D6 | `llvm20.tbl` / `llvm24.tbl` live in `compiler/src/backend/` and are read by `safeasm/build.rs` and `kernels/tests/safeasm.rs:421` | Move to `amdgpu-target` crate (`data/` dir, planned) in the same move as the rename and make both consumers hard-fail when the file is missing in a workspace build. |
| D7 | `dsl/specialize.rs` is used only by `amdc` | Leave in `amdgpu-dsl` for now; move with the JIT code later if `amdc` grows an L1 front. |
| D8 | `amdgpu-safeasm` is a verification-by-types layer for hand asm blocks; used by dsl, compiler, kernels | Stay a separate leaf crate. |
| D9 | kernel crate holds L3 / L4 probes and tests | Leave; revisit only if build time forces a split of `amdgpu-kernels`. |

## 3. Dependency problems found

Under the new layering. Result: the Cargo graph has **1 upward declared edge** (P1) and the source has **1 true
module-level upward edge** (P2); the other items are future crate-level cycles that the split would create or
coupling that is not a cycle yet. Cycles that the request expected but that I did **not** find are listed in 3.N.

### 3.N Cycles that were suspected but not found

The brief expected a cycle `stage <-> lds/shared <-> copy <-> pipeline <-> contract` inside `amdgpu-tile`. The `use crate::` edges are
(complete list from `git grep 'crate::' crates/amdgpu-tile/src`):

- `stage -> weave`; `pipeline -> lane, shared, weave`; `contract -> Ctx (lib.rs)`; `contract_stage -> layout only`; `handoff -> lib.rs (PrivRef)`;
- `copy -> mma, shared, Ctx`; `global -> copy, Ctx`; `dma -> rows, shared, weave, Ctx`; `bufdma -> shared, Ctx`; `rows -> shared, tensor, lib.rs`;
- `frag -> shared, lib.rs`; `epilogue -> frag, shared, tileop, lib.rs`; `softmax -> frag, reduce, lib.rs`; `reduce -> frag, pipeline (P2), lib.rs`;
- `opgraph/skeleton -> stage::registry`; `weave -> weave_auto`, `weave_auto -> weave`.

So: no L2 <-> L3 cycle exists; the one upward edge is `reduce -> pipeline` (P2). The only true module cycle is `weave <-> weave_auto`, both
moving to `amdgpu-codegen` (harmless if moved together; they must not be split across crates). `lib.rs` is a hub (`Ctx`, `add0`, `is_zero`,
re-exports) that most modules import and that re-exports them: after the split the hub items stay in the L3 `amdgpu-tile` and `amdgpu-stage` imports
them (downward), so no cycle, provided `lib.rs` does not re-export L2 modules (it does today: `lib.rs:255` `pub use pipeline::{...}`; this line
must go, see M7). The brief also expected "compiler depends on tile-level types" and "dsl <-> compiler": neither exists in Cargo.toml or in `use`
statements (compiler only has doc / comment mentions of "weave regions" and `stage`); `dsl` has one comment pointing at `amdgpu_compiler::gpu_verify`
(`dsl/lib.rs:1044`). Kernels use compiler only as a dev-dependency (36 test files), which is allowed (test crate is above).

Module-level cycles inside crates that move whole (`amdgpu-compiler` -> `amdgpu-codegen`, `amdgpu-dsl`, `amdgpu-kernels`): none found by
`use crate::` inspection of the compiler files listed in P12; `kernels` has `ir_proof -> gemm::GemmConfig` and `moe -> lds_decl` (acyclic).
I did not do a full automated cycle check of the 41 compiler / 53 kernels files; a script (`cargo modules` or a 20-line Python over `use crate::`) should
be run in M0 to confirm.
