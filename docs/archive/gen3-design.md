# Generation 3: one merged window per tile, rendezvous every R tiles with offset barrier placement

> Status: closed (negative) - the merged single window with offset barrier placement (`_g3`) was slower; see docs/current-status.md §5 and rounds 57-58 of docs/archive/status.md.

Status: design (kernel-opt), no implementation until kernel-occ's answer on barrier primitives. Baseline `fmha_fwd_hd128_mxfp8_vs128` 367.2 TFLOP/s; experiments `g2` (QK inside the V phase, 333.4) and `g3` (merged single window, one barrier per tile, 343.3) are documented in `docs/archive/kernel-gen2-design.md` §6-7.

## 0. The two facts the design rests on
1. Hardware overlap exists and is large when the work is independent (probes: 2 waves/SIMD, MFMA+VALU interleaved, wall = max + 0.27 min); QK inside the V window is hidden in `g2` (QK removal saves 0.3k of ~0.77k XDL cycles; WAIT_INST_ANY 543 -> 429).
2. The two obstacles measured: (a) the per-phase rendezvous with the partner group (`g2` WAIT_ANY 560 -> 813, wave cycles +161); (b) when both groups run the same phase of the tile at the same time (`g3`: no barrier between phases, no offset) the dependency stalls come back (WAIT_INST_ANY 429 -> 627) and the complementary pairing (+15%, measured by the `split1/2` lock-step layouts, -15%) is lost.
So the target: **keep the complementary offset between the two groups, remove the per-phase barriers.** gen3 gets there WITHOUT named barriers: `s_barrier` is count-matched, not PC-matched (the current kernel already puts A's and B's barriers at different program points in the prologue). Placing group A's barrier at the TOP of the tile pair and group B's barrier BETWEEN its V and M parts shifts B by one phase structurally, and the rendezvous happens once per R tiles instead of twice per tile.

## 1. Target schedule (R = 2)
Per group, per tile t: V(t) = max over the 4 S tiles -> rollback/bias apply -> for s in 0..4 {convert S_s; issue QK(t+1, s) into the freed registers}; M(t) = PV(t) (8 scaled MFMA) + smfmac row sums (4) + V transposed reads. (This is the `g3` window split at the P-word hand-over.)
Unrolled by R = 2 tiles, the loops are
- group A: `loop { BARRIER; V(2k) M(2k) V(2k+1) M(2k+1) }`
- group B: `loop { V(2k); BARRIER; M(2k) V(2k+1) M(2k+1) V(2k+2)' }` (rotated by one V phase; the V(2k+2)' of the last iteration is the first V of the next one - B's loop is entered at V(0) in the prologue; no carried registers: P(2k) is produced before B's barrier and consumed after it in the same iteration body).
At each barrier A is about to start V(2k) while B has just finished V(2k) and starts M(2k): A's VALU covers B's MFMA and vice versa; after the barrier the offset is one phase and stays one phase until the next barrier (both groups execute the same 2 windows between barriers, so neither waits for long). The barrier count per iteration is 1 for both groups (count-matched).
Steady-state budget per SIMD per tile (2 groups, 1 wave each), from the measured skeletons: V' = 1.15k VALU + ~0.1k of QK-MFMA issue and K reads = 1.3k; M' = PV 0.58k XDL + 32 transposed reads + dependencies = ~0.9k. Each SIMD completes one tile per group per iteration, in two windows: [V'(A) || M'(B)] then [M'(A) || V'(B)]. With the probe's overlap efficiency each window costs max + 0.27 min = 1.3 + 0.24 = ~1.55k, so ~3.1k for the two windows, + ~0.1k arrival skew per tile + the DMA issue 0.44k (already part of V' if the address VALU is counted there; 0.2k extra otherwise) = **~3.6k per tile (optimistic model, ~540 TFLOP/s)**. Corrections: dependency stalls inside each part (g3 showed WAIT_INST_ANY 627, about +0.2k per tile) and the VALU overhead (section 4) bring the central estimate to **~4.3k (~420 TFLOP/s)**; the conservative bound is `g3` (343, lock-step, one barrier per tile) times the measured pairing factor 1.15 = **394 TFLOP/s (+7%)**. Predicted range **394-540, central ~420 (+14%)**.
Drift budget: per-tile jitter of one group relative to the other ~+-5% (+-0.25k); over R = 2 tiles it accumulates to <= 0.5k, well below the half-window (1.3k) that destroys the complementarity, and the barrier resets the pair every 2 tiles; the arrival skew at the barrier (A waits for B or vice versa) is the max of two jitters ~0.12k per barrier = 0.06k per tile.

## 2. Ring depth and DMA prefetch distance for R = 2
Constraints (windows are tile indices; the barrier is every R windows; a DMA is waited at the end of the window it is issued in by its issuing wave, so its data is visible to all waves only after the NEXT barrier):
- visibility: first read window F >= i + R for a DMA issued in window i (worst case: i is a barrier window);
- reuse: the previous occupant's last read L' must precede the last barrier at or before i: worst case S >= (L - F) + 2R slots for a ring whose entries are read in windows [F, L] (relative to the tile index).
K and V have different lifetimes, so the ring is SPLIT (16 KB slots instead of 32 KB K+V slots): K tile t is read by QK(t) in window t-1 for group A and in window t-2 for group B (B's V phase is one phase ahead): L - F = 1 -> S_K = 1 + 4 = **5 slots (80 KB)**, issued R + 2 = 4 windows ahead. V tile t is read by PV(t) in M(t) of both groups after the barrier: L - F = 0 -> S_V = 4 slots (**64 KB**), issued R = 2 windows ahead. K scales follow the K ring (5 x 512 B). **Total 144 KB + 2.5 KB = ~147 KB <= 163840 B.** R = 3 would need S_K = 7, S_V = 6 (208 KB): not possible; R = 1 (today's single-barrier-per-tile form) needs 3 + 3 slots = 96 KB (that is `g3`).
DMA prefetch distance: K 4 windows ahead, V 2 windows ahead; the prologue stages min(nkv, 4) K tiles and min(nkv, 2) V tiles; clamping for short sequences follows the existing `key_n2` select logic. The Q staging region (34 KB) is already gone (resident Q).

## 3. Fallbacks if the barrier trick (count-matched `s_barrier` at different PCs) were illegal or too slow
(a) Two blocks of 4 waves: one block per CU (the 147 KB ring does not allow two) = 4 waves/CU = 1 wave/SIMD. Arithmetic: B1H8S2048 = 8 x 8 = 64 blocks of 256 rows today; with 128-row blocks 128 blocks (< 256 CUs, still no underfill). One wave per SIMD has no partner to hide latency: the probe's single-wave overlap is 66% (927 vs 791/604/1395), per tile ~max(1.15, 1.5) + 0.34 min = 1.9k per tile per SIMD, i.e. 0.53 tiles/k per SIMD vs 0.37 now (+41% if the overlap is realised) - but 1 wave/SIMD lifts the register ceiling to 512 (VGPR + AGPR), which would also allow a double-buffered S. Costs: K/V global/L2 traffic per FLOP doubles (a 128-row block loads the same 32 KB K/V tile per 128 keys for half the FLOPs: ~17 B/cycle/CU at 1.9k cycles per tile), the whole kernel is a new design with explicit software pipelining (probably `Stmt::Asm`). Not rejected on occupancy (the grid still fills), only on risk; keep as option E.
(b) Asymmetric roles: group A owns the ring/DMA (stages K and V) and runs a lighter compute share, group B pure compute, one barrier per tile: needs unequal query-row ownership (A 16 rows/wave, B 48?) - breaks the 32-row MFMA tile geometry; rejected.
(c) Software pipelining across tiles with tile state in LDS: S/P in LDS costs +256 KB/CU-tile of LDS traffic (LDS 2.0k -> 4.0k cycles per tile at 128 B/clk): LDS-bound, rejected (same as option B of the gen2 doc).
(d) Accept `g3` and shorten the dependence chain: split the P conversion so PV half 0 can start earlier. Measured `g3pv` (PV half 0 between the conversions of tiles 1 and 2): 322 (worse); an uneven split (PV half 0 after tile 0 only needs a 4-word P fragment: the PV MFMA K dimension is 64 keys = 2 tiles, so tile-granular PV is not possible) - rejected by the MFMA shape.

## 4. VALU: where `g3` loses +33 against `_vs128` (static loop counts, long-sequence copies)
`_vs128` A-loop 291 VALU, B-loop 281; `g3` A-loop 324, B-loop 313. By class (A-loop): INT 51 -> 74 (**+23**), CMP/SEL 21 -> 27 (+6), MOV 28 -> 32 (+4); CVT 70, PK 64, MAX 33, F32 21 identical. Source: the per-tile calls of `qk` recompute loop-invariant-per-iteration values per call: `kfb[k] = kfx[k] + slot` (4 adds), `kd_rd`, the K-scale address adds, the `so`/`ko` offsets and the `Select`s of the ring helper are re-emitted for every S tile instead of once per iteration (the compiler does not CSE across closure calls). Hoisting them (compute `kfb`, `kd_rd`, and the per-tile `ko` constants once per window, pass them in) removes about 24 VALU (6.8% of 352) and the MOV/CMP deltas follow. gen3 therefore plans ~352 - 24 + (barrier-position bookkeeping 0) = **~330 VALU/wave-iteration** (the model above already used 1.15k for the V part; this saves a further ~0.1k per tile).

## 6. Implementation result (kernel-opt): the offset barrier placement does not recover the complementary pairing
**Step 1 - hoisting the per-window values** (`g3`, option `nohoist` disables): static VALU of the loops -30 (3828 -> 3798 over both roles, i.e. -15 per role-loop: `kfb`/`kd_rd` = 5 adds per extra `qk` call; the INT +23 of §4 was partly the ring selects and the per-call sh16/ko adds, which are per-tile in `_vs128` too), but the five extra live registers push `g3` (254 of 256 VGPR) over the edge: the scheduler falls back to the unscheduled code ("out of VGPRs allocating r765 (V16 ...)") and the time drops 344.4 -> 325.8. Not usable at the current register level.
**Step 2/3 - `fmha_fwd_hd128_mxfp8_g3o`** (own backend, by name only): one merged window per tile, ONE barrier per tile at the top of the window for group A and after the V part for group B (count-matched, B one phase ahead), 4-slot combined ring (tile t+3 staged right after each group's barrier; LDS 133120 B; the Q/ones staging stores are dropped), Q resident, smfmac, exact reference. Output **bit-identical** to `_vs128` (1 8 2048 2048; md5 faadf00c) and correct on 1 1 256 256 / 1 2 512 400. B1H8S2048: **334.6 TFLOP/s** (vgpr 253) vs `_vs128` 367.2 and `g3` 343.3; schedulers `AMDC_SCHED=0` 329.0, `ld` 331.9.
Counters per wave-iteration (g3o | g3 | `_vs128`): WAIT_ANY 650.0 | 557.6 | 560.4; WAIT_INST_ANY 587.1 | 627.3 | 543.4; wave cycles 1757.7 | 1702 | 1599; VALU 371.1 | 385.6 | 352.1; LDS 52.6; MFMA busy 1216; IFETCH 104.8.
Ablations of g3o: `nobar` (no barrier at all: the two groups free-run, offset only from the start) **302.7**; `novalu` 361.8; `noqk,nopv` 405.8; `nodma` 347.1; `nodma,nobar` 369.9.
Interpretation: with the barrier moved to the offset position the per-window rendezvous skew (A waits for B's V part) shows up as +92 WAIT_ANY over `g3`, while the dependency stalls (587) fall only slightly; the free-running ablation is WORSE (302.7) than any barrier placement: without the periodic re-synchronisation the two groups drift into unfavourable alignment, so a rendezvous every R = 2 tiles (the design's R) is expected to land between the R = 1 result (334.6) and the free-running 302.7 - below `_vs128`. The model's assumptions (offset persists for 2 tiles; skew ~0.12k) do not hold: the per-window skew is ~0.4k (92 cycles per wave-iteration x 4.3) and the drift is destructive, not neutral. R = 2 with the split K/V ring (147 KB) was therefore NOT implemented: its best case is bounded by the R = 1 measurement and the free-running bound. Final negative of the gen3 line; `_vs128` stays the fast path.

## 7. Option E (4-wave blocks, 1 wave per SIMD) bounded on paper
**Two different things are called "option E"; only one is comparable.**
- **E1: 128-row blocks (grid x2).** The harness (and the vendor ABI) launches `((S+255)/256, H, B)` blocks of 512 threads: B1H8S2048 is 8 x 8 x 1 = **64 blocks on a 256-CU GPU, i.e. 25% of the CUs are idle for BOTH our kernel and the vendor's** (367 TFLOP/s is ~7% of the MXFP8 peak for this reason). 128-row blocks would double the busy CUs (128) and therefore "win" 2x on this shape whatever the kernel does - a benchmark-underfill artifact that needs a different grid than the drop-in ABI (the host would have to launch 2x blocks) and vanishes for shapes with >= 256 blocks. It is not an efficiency gain and is excluded from the comparison below. K/V L2 traffic per FLOP doubles (a 128-row block loads the same 32 KB K/V tile for half the FLOPs: ~17 B/cycle/CU at 1.9k cycles per tile vs ~6 now).
- **E2: ABI-preserving 4-wave blocks.** Grid and rows per block unchanged (256 rows), 4 waves of 64 rows each = two independent 32-row sub-tiles per wave, 1 wave per SIMD, 512 VGPR (256 arch + 256 AGPR) per wave. K/V fragments are read once and used for both sub-tiles (LDS reads per FLOP halve); the two sub-tiles supply the independent work that the partner wave supplies today.
**Per-SIMD arithmetic for E2** (per 64 rows per tile; skeleton resources per 32-row tile: XDL/LDS 1.5k, VALU 1.15k; current wall 5.37k):
| case | assumption | wall per tile | vs 367.2 |
|---|---|---|---|
| lower bound | the measured occupancy sensitivity of the dependent kernel: 1 -> 2 waves/SIMD = 1.25-1.93x | 6.7k-10.4k | 0.52-0.80x (-20..-48%) |
| upper bound | the probe: one wave overlaps independent MFMA+VALU at 66% (927 vs max 791 / sum 1395; the 1-wave and 2-wave probes cost the same per unit of work: 927 vs 898); XDL/LDS 2 x 1.5k = 3.0k (2.6k with the shared K/V reads) + 0.34 x VALU 2.3k = 0.8k | **3.4-3.8k** | **1.41-1.58x (up to ~520-580 TFLOP/s)** |
So the arithmetic does NOT prove "no": the occupancy-loss lower bound (-20..-48%) is for a kernel whose dependences the partner wave hides; E2's upper bound requires the instruction stream of the two sub-tiles to be interleaved by hand at instruction granularity (what the list scheduler failed to do inside a tile: `g2`/`g3`/`g3o`). The probe bound is reachable only if that interleave is as good as the probe's.
**What E2 additionally needs and costs (not in the bounds above):** (1) AGPR support in the DSL/backend (the compiler allocates at most 256 VGPR; the 512-register budget needs MFMA accumulators/outputs in AGPRs); (2) VALU access to AGPR values costs `v_accvgpr_read/write`: reading S for the max/convert (64 per S tile set per sub-tile, +128 VALU per tile) and the O rescale on a rollback (64 reads + 64 writes + the multiplies, ~3x the current rollback cost of ~1.15k) unless O stays in VGPRs (128 of 256) and only S/P/Q go to AGPRs; the VALU budget per tile therefore rises from 352 to ~480-600 per 64 rows, which moves the "VALU-bound" point in the model (VALU 2.3k -> 3.0-3.5k per tile: the upper bound becomes ~3.8-4.2k, i.e. +28-41%); (3) a hand-authored loop (`Stmt::Asm`) for the interleave, and a prologue/epilogue/mask/tail variant of it.
**Conclusion.** E1 is an artifact, not an option. E2's lower bound is far below `_vs128` and its upper bound (+28..+41% after the AGPR costs) is above it, but the upper bound needs three things that do not exist today (AGPR allocation, a hand-interleaved two-sub-tile instruction stream, and a VALU diet): it is a next-generation kernel project, not a tuning step, and every scheduling-level attempt in this line (`g2`, `g3`, `g3o`, `_vsm`, prefetch variants) landed on the lower side of the same dependence argument. Expected value on today's tooling: negative.
