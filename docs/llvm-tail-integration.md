# LLVM tail integration ("our middle end + LLVM tail")

NOTE (round 3): the primary pin is now ROCm 10.1.0 (AMD LLVM 24.0.0git, dialect `llvm24`), ROCm 7.0.2 (`llvm20`) stays supported; see docs/llvm-tail-conformance.md. Numbers below were measured with 7.0.2 unless stated.

Status: prototype on branch `backend-tail`. Evidence grades: **Verified** = measured/observed in this
repo on the node (ROCm 7.0.2, `AMD LLVM version 20.0.0git`, 8x MI355X); **Experimental** = works in our
tests but not understood/measured beyond that; **Unknown** = not investigated.

## 1. Architecture

```
DSL -> lower.rs (SSA/MIR, our waits) -> hazards.rs (in-block fill, own nops) -> regalloc.rs
    -> TailBackend::finish(MFunction, Alloc)
         OwnTail  : emit.rs text + hand-written descriptor            (default, unchanged)
         LlvmTail : backend/llvm_mir.rs  -> post-RA MIR text
                    llc -start-before=gcn-create-vopd -filetype=asm   (tail passes only)
                    -> .s (LLVM also writes the kernel descriptor + metadata) -> clang -> .co
```

`amdc emit K --backend llvm-tail --out K.s` (`AMDC_BACKEND` env also works; `--mir-out f.mir` writes the
exported MIR only and needs no LLVM). `ROCM_LLVM_BIN` (or `ROCM_PATH`) selects the tool directory.
`tools/container/cargo.sh` takes `AMD_ROCM_MOUNT=<rocm>` to mount ROCm read-only into the build container
so `llc` is runnable there; `tests/gpu/run.sh` / `run_ref.sh` honour `BACKEND=llvm-tail`.

Tail passes after the start point (Verified, from `backend.lock`): `gcn-create-vopd, si-memory-legalizer,
si-insert-waitcnts, si-mode-register, si-insert-hard-clauses, si-late-branch-lowering,
si-pre-emit-peephole, post-RA-hazard-rec, amdgpu-wait-sgpr-hazards, amdgpu-insert-delay-alu,
branch-relaxation, ...`. None of them reorders instructions (Verified: for `fmha_fwd_hd128_mxfp8_t` the core
instruction stream of both backends has the same length and, after normalising cosmetic operand
printing, is identical; see 5). `gcn-create-vopd` is a no-op on gfx950 but WILL pair/reorder VALU ops on
gfx1250 (Unknown, to be re-checked by `amdc backend check` + the oracle on that target).

## 2. Version coupling surface (all behind one adapter)

| Coupling | Where | Guard |
|---|---|---|
| (a) MIR text + opcode/operand shapes | `backend/llvm20.tbl` (DATA, one row per MOp/operand-kind), `backend/llvm20_header.txt` (function header), `backend/llvm20.rs` (token renderer, S_WAITCNT encoding) | test `opcode_probe_every_row_assembles`: one tiny MIR per row through the pinned llc with `-verify-machineinstrs`; a version bump shows exactly which rows broke. `table_has_a_row_for_every_mop` |
| (b) pass names / start point | `backend.lock` + `backend/probe.rs` | every LlvmTail emit re-checks `llc --version`; `amdc backend check` compares the whole tail pipeline, requires `si-insert-waitcnts` + `post-RA-hazard-rec`, and FAILS if any of `postmisched, machine-scheduler, post-RA-sched, block-placement, ...` runs after the start |
| (c) IR shell attributes | header template | descriptor equality is checked by the oracle (user_sgpr_count 2, wg ids xyz, ieee 0, denorm 3 ...) |
| (d) assembler syntax | `.s` is produced by LLVM itself; our own text is only used by OwnTail | - |

A new LLVM = new `llvmNN.{rs,tbl}` + header, `amdc backend write-lock` after the probe test and the oracle
(section 5) are re-run and the new "erratum changelog" has been read. llc is never linked, LLVM sources are never touched.

## 3. Export decisions (Verified unless noted)

* **Instruction order, registers, block layout** pass through unchanged. Fallthrough `s_branch` to the next block is omitted (LLVM drops it too).
* **Own `s_nop`** is dropped (`SNop` row = DROP); LLVM recomputes all hazards.
* **Waits**: every `s_waitcnt` (explicit DSL waits *and* the ones `lower.rs::touch()/flush_pending()` inserts) is kept as a hard `S_WAITCNT`. `SIInsertWaitcnts` merges pre-existing waitcnts with what it needs, it never loosens them. Across all 41 kernels LLVM added no waits that we lacked: `llvm_wc <= own_wc` everywhere (it only removed duplicates, e.g. two consecutive `lgkmcnt(0)`), i.e. our auto waits are a superset of what LLVM computes. Cross-wave LDS visibility (`wait_lds` before `s_barrier`) therefore never depends on LLVM. Deleting our auto waits is the plan in section 7, not done.
* **Header**: IR shell + MIR function header come from a template generated by `llc -stop-before=gcn-create-vopd` on the shell. Needed attributes: `amdgpu-flat-work-group-size`, `amdgpu-ieee=false`, `amdgpu-no-{dispatch-ptr,queue-ptr,dispatch-id,implicitarg-ptr,heap-ptr,multigrid-sync-arg,lds-kernel-id,completion-action,hostcall-ptr,workitem-id-y,workitem-id-z}`, `target-cpu=gfx950`. With them LLVM emits `.amdhsa_user_sgpr_count 2`, kernarg ptr in s[0:1], workgroup ids s2/s3/s4, `workitem_id 0`, `ieee_mode 0`, denorm 3: the same ABI our own descriptor declares.
* **Kernarg layout**: LLVM lays IR kernel parameters out packed/naturally aligned and derives `.amdhsa_kernarg_size` from them. The DSL (vendor ABI) layout is sparse (16-byte spaced scalars, 16-byte `abi_tail`), so the IR signature is padded with dummy `i64/i32/i8` parameters up to `kernarg_size`. Without this `.amdhsa_kernarg_size` was 140 instead of 656 and the kernel hit an illegal memory access (Verified failure and fix). Side effect: the pad parameters show up in the `.args` metadata (harmless for `HIP_LAUNCH_PARAM_BUFFER` launches; `attention_fwd` has a natural layout and no pads).
* **Liveness**: per-block `liveins:` are computed by a backward dataflow over physical dwords taken from the *rendered MIR text* (so the table is the single source of truth, including implicit `$vcc/$scc`).
* **MachineMemOperands**: address space + size only (`:: (load (s32), addrspace 3)`), no IR value, no atomic ordering/syncscope yet (Unknown whether any DSL op will need `si-memory-legalizer` cache-policy bits; later).
* **LDS size** via `ldsSize` in the header; `amdhsa_next_free_vgpr/sgpr`, `accum_offset` are computed by LLVM from the registers used.

## 5. Oracle: what LLVM inserts that our model lacks

Tools: `tests/hazard_oracle.rs` (pairwise matrix; `AMDC_ORACLE_OUT=/work/build/matrix.md` writes it plus `.s/.mir`;
summarise with `tools/oracle_summary.py [--detail]`), `tools/hazard_oracle.sh` (per kernel), `tools/asmdiff.py`
(stream diff, `waits|nops|classes` modes).

The matrix feeds every (producer row, consumer row, source slot) pair *back to back* with a data dependency
(or implicit vcc dependency) through the tail: 3832 pairs, each in its own block separated by `s_nop 15 x2` and a full wait,
and compares LLVM's inserted `s_nop` cycles with what `hazards::fix_value_hazards` pads for the same pair.
These are LLVM's requirements at distance 0 (grade **Verified as LLVM behaviour**); whether the hardware really needs each of them is **Unknown**, we did not measure it (the kernels that passed hardware did so with our smaller set, the LLVM ones are a safe superset).

LLVM requires wait states our model lacks (class pair: LLVM nop cycles vs ours):

| producer -> consumer | LLVM | ours |
|---|---|---|
| any VALU write of a VGPR -> MFMA operand (A/B/C/scale; e.g. `VAddF32/VMulF32/VCvtPk*/VCndmask/VWriteSub ... -> VMfma*`) | 2 | 0 |
| VALU carry-producing (`v_add_co_u32`, `VPtrAdd`) -> MFMA operand | 4 | 0 |
| VALU (incl. cvt, readfirstlane producers) -> `v_readfirstlane` | 1 (2 after readfirstlane->VALU) | 0 |
| vcc writer (`v_cmp*`, `v_add_co`, `v_addc_co`, `v_cndmask`) -> carry consumer (`v_addc/v_add_co` reading vcc) | 2 (up to 4 after carry) | 0 |
| `v_cmp*`/`v_add_co` -> `v_cndmask` (vcc as mask) | 2 | 0 (verifier only forces adjacency) |
| VALU-cvt (`v_cvt_pk_*`) -> next VALU/cmp/cndmask/trans | 0..1 (forwarding hazard) | 0 |
| DS read/write, VMEM load/store, SALU -> `v_addc/v_add_co` (sgpr/vcc operand) | 0..2 | 0 |
| global_load -> global_store data (observed in the probe blocks) | 1 | 0 |

Where we are MORE conservative than LLVM (candidate savings, still Unknown for hardware):

| producer -> consumer | ours | LLVM |
|---|---|---|
| `v_exp/v_rcp` -> VALU/MFMA/DS/VMEM | 5 | 1 (VALU), 2 (MFMA), 0 (DS/VMEM) |
| MFMA (12/20 table) -> DS write | 12 | 8 |
| MFMA -> VALU/tuple read | 12/20 | 8..20 (depends on the MFMA pass count) |
| dependent MFMA -> MFMA (SrcC chain) | 0..20 | 0 (hardware forwarding; our model pads for the VALU case only, the oracle shows ours 0..20 over MFMA consumers) |

Per kernel (`tools/hazard_oracle.sh`, s_nop cycles): `attention_fwd` 10 vs 12, `probe_fp8_fmha_abloops` 42 vs 68,
`probe_fp8_fmha_hd128c` 476 vs 810, `fmha_fwd_hd128_mxfp8` 498 vs 814, **`fmha_fwd_hd128_mxfp8_t` 172 vs 820 (362 `s_nop`)**.
Dominant class in the `_t` kernel (319 instances, 686 cycles): adjacent `v_cmp_* vcc` -> `v_cndmask_b32 ... vcc` pairs, `s_nop 1` each (the softmax
masking idiom), then `v_add_co_u32 -> v_addc_co_u32` 102 cycles, `VALU -> MFMA` `s_nop 1`. Full table: run the script.
Waits: LLVM never adds waits to our output; `s_delay_alu` is never emitted on gfx950.

Interpretation (Experimental): the LLVM tail costs `fmha_fwd_hd128_mxfp8_t` roughly 650 extra issue cycles (static count) that are
inside the softmax/masking sequences. The 15-shape correctness check passes with either tail. Timing of the LLVM-tail `.co` against the own-tail `.co` is NOT measured yet
(the lead/kernel teammate owns GPU 0 for timing); the static numbers are not a performance claim. A scheduler that knows the LLVM rules could hide the
nops (the `cmp -> cndmask` pairs can be separated by independent work) because the hazard recognizer only pads what is adjacent.

Cosmetic differences between the two outputs (all semantically identical, Verified by `asmdiff.py`): operand order of commutative `v_add_co_u32_e32`, hex vs decimal immediates / `4.0` inline float printing, `op_sel_hi:[0,0,0]` printed on scaled MFMA, `s_load` offsets in hex, dropped fallthrough `s_branch`, `.sgpr_count` 50 vs 48 (LLVM reserves vcc), longer descriptor.

## 6. Open issues / limits

1. `S_WAITCNT` encoding in `llvm20.rs::waitcnt_imm` is gfx9-only (gfx1250 has separate `S_WAIT_*` instructions): per-version code, covered by the opcode probe.
2. No atomic/ordering MMOs yet; no `align`/`volatile` on MMOs. LLVM's hazard rules that look at memory operands (e.g. LDS-DMA, scratch) will not see them.
3. MFMA MIR uses the `_vgprcd` untied pseudos even when D == C. Verified by the probe/verifier for D != C; D == C kernels pass on hardware.
4. The oracle measures adjacency only; LLVM's nop counts for pairs at distance > 0 (partially covered hazards) follow from its wait-state counting and are not enumerated.
5. A `-verify-machineinstrs` run of whole kernels is available through `AMDC_LLC_ARGS=-verify-machineinstrs` (`llvm_tail_assembles_kernels`); the unit probe uses it per opcode. Whole-kernel verification with the liveness checks enabled has not been made part of CI (Unknown: some `killed/dead` flags are not exported).

## 7. Plan (not implemented): retire our own wait/hazard code, scheduler interface

1. **Flag** `--own-hazards=off|on` (default on) that skips `hazards::fix_value_hazards` padding for LlvmTail (keep the in-block gap-filling scheduling, it is a schedule, not a hazard model). Use the oracle to prove that `off` + LlvmTail passes the 15 shapes, then flip the default for LlvmTail only.
2. **Waits**: tag the `S_WAITCNT` that `lower.rs::touch/flush_pending` inserts as `auto` (new `MInst` flag, additive) and let the exporter drop `auto` waits; keep DSL waits (`wait_lds`, barrier-adjacent). SIInsertWaitcnts then computes vmcnt/lgkmcnt itself. Acceptance: oracle `llvm_wc` for each kernel, GPU regression 15 shapes, plus a targeted LDS-handoff kernel (`probe_lds_self2`, `probe_waves2`) since cross-wave visibility is the one thing LLVM cannot see.
3. Once 1-2 pass on hardware, delete `hazards.rs` padding and the `touch()` machinery behind `#[cfg(feature = "own-tail")]`, keeping OwnTail only as the reference backend until LLVM 10 is validated.
4. **Cross-block scheduler interface**: it runs on the allocated `MFunction` (or before RA with the same MIR) and only permutes instructions inside/between blocks; the contract is: output = `MFunction` + `Alloc`, every dependency incl. implicit `vcc/scc/exec` and waits preserved. Because no tail pass reorders, the scheduler may use the hazard oracle matrix (`llvm20` nop table extracted from `matrix.md`, regenerated per LLVM) as its cost model: `cost(P,C,distance) = max(0, required_states(P,C) - distance)`. The export is the only place that must change when the scheduler introduces new block shapes (it needs `successors`/`liveins`, both already derived from the terminators).
5. `gcn-create-vopd` (gfx1250) re-pairs VALU ops: when gfx1250 lands, either start the tail after it (lock check will flag the pass list) or schedule for it.

## 9. Default backend and ownership (round 3)

* **Default = `llvm-tail`** (dialect `llvm24`, ROCm 10.1.0, `backend.lock`). `amdc emit --backend=own` (or `AMDC_BACKEND=own`, `BACKEND=own` in the GPU scripts) selects our complete own tail. `compile()` in the library keeps meaning OwnTail (library API stability); the CLI and all scripts default to the LLVM tail. If the pinned tool directory cannot be run, `llvm-tail` fails with a message suggesting `--backend=own`; there is no silent fallback to another LLVM. ROCm 7.0.2 (`llvm20`) stays selectable (`ROCM_LLVM_BIN`, `AMDC_DIALECT`).
* **Who owns what.** Always ours, in both backends: DSL, lowering, MIR, register allocation, instruction scheduling (`--sched`, `--sched=auto`, swp, taildup), block layout. LLVM tail only: hardware waits (`s_waitcnt`, merged with our explicit waits), hazard nops / `s_delay_alu`, memory legalizer, mode register, branch relaxation, kernel descriptor + metadata. The one extra instruction class LLVM may add is a hazard workaround (observed: `s_mov_b64 vcc, vcc` before an `s_cbranch_vccz` in the `sched_diamond` taildup build).
* **Invariance test** (`tests/tail_invariance.rs`, in `cargo test`): for every kernel the normalised instruction stream (opcode, physical registers, order) of own and llvm-tail is identical modulo `s_nop/s_waitcnt/s_delay_alu/s_branch` and operand spelling (hex vs decimal, inline floats, commuted `v_add_co_u32`, `op_sel_hi:[0,0,0]`, labels); the exported MIR is `noVRegs: true` with no virtual-register operand; group-segment and kernarg sizes agree and LLVM's `next_free_vgpr` covers our allocation. Verified (48 kernels) with the scheduler off and with `AMDC_SCHED=1`, `swp`, `taildup,swp`, `auto`. This is the regression protecting "register allocation and scheduling stay ours": if LLVM ever re-allocated or reordered, the stream would differ.
* **`--sched=auto`** (`AMDC_SCHED=auto`, default scheduler stays OFF): `sched::auto_plan` simulates each loop (`sched/sim.rs`, average of 1 and 2 waves/SIMD) and schedules only loops whose model improves by >= 3% (`AUTO_GAIN`); swp keeps its own >= 3% gate; taildup is enabled only if the loops common to both trial results improve >= 3% in total. Loops with `s_barrier` are excluded (the model has no cross-wave barrier term; it predicted -23% for the FMHA loops where hardware measured 221.7 vs 225.0 TFLOP/s) unless `AMDC_SCHED_OPTS=trustmodel`. `AMDC_SCHED_OPTS=stats` prints the per-loop decisions. Compile time: instant when no loop is eligible (FMHA), seconds for the microkernels, ~2 min for `attention_fwd` (large single loop evaluated several times).
  Measured on hardware (GPU 4, `tools/auto_vs_plain.sh`, cycles/iteration, 1 wave / 2 waves per SIMD, auto vs plain): sched_valu_mul -37%/-36%, valu_max3 -35%/-22%, valu_exp -23%/-14%, mfma_chain -40%/-1%, mfma_valu16 -37%/-15%, mfma_valu4 -56%/-24%, diamond -32%/-14%. FMHA B1H8S2048 (TFLOP/s, 3 reps): own 224.6-224.7, llvm-tail 224.0-226.3, llvm-tail+auto 224.7-225.6 (identical code to llvm-tail: auto leaves FMHA unscheduled).
* Open conformance items: kill/dead flags not exported (3 LLVM peephole tests skipped, conservative), MMO atomic/LDS-DMA information when the DSL needs it, 2 verifier cases (`waitcnt.mir`, `waitcnt-agpr.mir`, not root-caused).

## Kernel exposure policy: `kernel_names()` vs reachable-by-name

`kernel_names()` lists the kernels that every sweep (LLVM-tail MIR export, `tail_invariance`, metadata, conformance, `register_accounting`) enumerates, i.e. kernels that compile through BOTH backends. Kernels that use own-backend-only MOps (the LDS-DMA loads `GlobalLoadLdsB128/B32`: `probe_dma*`, `fmha_fwd_hd128_mxfp8_vs`, `fmha_fwd_hd128_mxfp8_vs128`) are registered in `kernel_by_name()` only; `amdc emit <name> --backend own` builds them, the LLVM tail refuses them (the llc has no rows for those MOps). Tests that sweep the LLVM tail skip any kernel whose MIR contains a DMA MOp (`llvm_tail_supported`), and `tests/register_accounting.rs` audits the own-only kernels by name (`DMA_PROBES`, which now includes `_vs` and `_vs128` as far as they allocate) so the descriptor/register audit still covers them.

## Register allocation: ghost liveness, hole-aware packing, remat, LDS spill (round 6)

* **Ghost liveness (a model error worth remembering).** Block-level vreg liveness with "a definition kills" is wrong for fragments built lane by lane (`VWriteSub`) and keeps slots live that are read on an infeasible path with no reaching definition (correlated `if`s): 64 V1 were "live at function entry" in `_t`. Our first pressure numbers for `_vs128` (269-287 dwords, "infeasible") came from that model, and a first "allocates in 238" result came from the opposite error (lane-built fragments dying between their lane writes) - the hardware run caught it (2/15 shapes) and the physical reaching-writer test failed. The corrected model: dword-level liveness from the scheduler's effects model, intersected with forward may-defined sets (`regalloc::precise_segments`, `pressure_profile`). With it `_vs128` has a true peak of 254 dwords (`dce,cmpfold,scalarize`), 234 with `imm`, and allocates (vgpr_count 254).
* **Policies.** `allocate()` tries the compact scan, then singles-from-top, then (last resort) the offline two-phase packing: wide tuples first (widest, longest), singles into holes in time, using the pruned dword-level segments; its result is re-checked with `regalloc::check_reaching` (physical reaching-writer analysis) and rejected if any read sees a wrong writer. `AMDC_RA_FORCE_TWOPHASE=1` forces it for testing: `_t`, `_vs`, `_sv`, `_pp`, `attention_fwd` stay correct (and `_t` bit-exact 15/15), `mir_invariants`, `register_accounting`, `dead_loads`, `tail_invariance` are green with it.
* **Pruned liveness as the DEFAULT liveness for the scan policies: tried, not adopted.** Using the hull of the pruned segments for the scan policies made scheduled `_t`/`_sv` fall back to the unscheduled code (out of VGPRs) and `_t` through the LLVM tail was no longer bit-exact (2/15; LLVM also deleted ~63 `v_mov` as dead, i.e. its CFG liveness disagrees with the pruned one on those ranges) although our own reaching-writer check was clean. Lesson: a liveness model that is "more precise" than the consumer's (LLVM's liveness on the exported MIR) is not automatically safe; the pruned model is therefore only used where it was validated end to end (two-phase, forced on all kernels, plus the vs128 hardware run 15/15).
* **Retry ladder (only after an `out of VGPRs` failure, so kernels that allocate are untouched):** none, `remat1..3` (loop-invariant constants rematerialised next to their loop uses), `remat4` (whole constant/SGPR/tid expression trees), then `imm` + `ldsspillN`. **LDS spill** (`AMDC_RA_LDS_SPILL=N`, `ldsspillN`): peak-driven iterative spilling of loop-invariant V1 values to a per-wave LDS area (2048 B per value across 8 waves, lane*4 addressing = bank-conflict-free, `ds_write_b32` after the definition, `ds_read_b32` reload per use block, or per use at the peak block; base = declared `lds_bytes`). It lowers the peak only ~0.5 dword per spilled value, was NOT needed for `_vs128`, and is kept as a documented capability. `sink` (definition sinking) and `remat` had no effect on vs128.
* **Backend auto-selection:** `amdc emit` defaults to `--backend=auto`: `llvm-tail` unless the kernel's MIR contains own-only ops (the LDS-DMA loads), then `own` with a one-line note; explicit `--backend=own|llvm-tail` are honoured (`llvm-tail` on a DMA kernel fails with the missing-table-row error). `tests/backend_auto.rs`.
* `pad_physical_war` (MFMA operand write-after-read) now also runs on the unscheduled path (`AMDC_NO_PHYS_WAR=1` disables): register reuse from the packing can place a new value in a register an in-flight MFMA still reads.
