## 2. Code review: are the kernels written in abstractions?

**Verdict: mostly yes.** `fmha_tile.rs` is **501 lines for all four kernels**, versus ~3,800-4,800
lines in the legacy `fmha_t_build`/`emit_fmha_*` paths. Each kernel builder is 35-75 lines:
tensor declarations (`FmhaIo::declare`), one 2-/3-slot `KvRing` (`LdsPlan`), one `Pipeline` with a
`Cadence`, and an `AttnBody` (`OnlineSoftmax`, `qk_tile`, `pv_tile`, `AccTile`). Kernel code contains
**no** `tile_produce/tile_consume`, no DMA instruction, no `wait_lds/wait_vm`, no per-lane MFMA
addressing and **only one hand-written `barrier()`** (the kvsplit epilogue). Markers/generations are
generated by `Pipeline`/`Shared`, reads by layout types (`Frag::<...>::load_*`), writes by
`RowsCopy`/`DwordRowsCopy`/`DwordRowsVgpr`, softmax by `OnlineSoftmax`, epilogue by `store_bf16`/
`kvsplit_partial_f16`/`combine_splits`.

Remaining hand-written low-level spots (line refs in `fmha_tile.rs`):

| lines | what is hand-written | why it remains |
|---|---|---|
| 48-49, 77-89 | scalar shape/GQA/grid/KV-split contracts (`ka_range`, `ka_is`, `grid_is`, `arg_tensor` for V descale/Ohat/lse) | scalars/extension fields are not tensors; could move to `KArgs`/components |
| 99-135 | block ids, `row0 = (qTile << rows_lg) + (wave << 5)`, row clamp, `q_off` with `lane.half() << 4`, `nkv` trusted assume | block/lane mapping has no higher-level tile iterator yet |
| 223 | `_t128` K-scale VGPR staging row `tid >> 1` | hand row mapping inside a library copy selector |
| 293-306 | constant LDS prologue: `wid*64 + lane`, `wid*2048 + sh.base + (lane<<4)`, `+1024`, direct `store_lds_b32/b128` | `ones`/Q staging writes are hand addresses; `Shared::write` wraps the marker but not the address algebra |
| 391, 496 | output pointer `lane.half() << 2`/`lane.j()` in `store_bf16` row ptr | epilogue row-to-tensor mapping |
| 421-444 | kvsplit epilogue: hand `b.barrier()` at 425, `prow` formula, `lse_ptr`, Ohat offsets `(prow << 8) + ((lane&7)<<4)` | epilogue component takes a closure for the Ohat pointer; no `Tensor::ptr` is exposed here |
| 464-470 | combine thread/group mapping `groups = rows << 4`, `t = clamp(bx<<8 + tid)`, `row = t >> 4`, trusted assume | combine is a flat-1D launch; `combine_splits` owns the algorithm but not the launch mapping |
| 347-353 (`loop_state`/`bind_state`) | explicit loop-state variable layout (`[0,9]`, `[1..5]`, `[5..9]`) | struct/`PipeBody` state is positional by design (no struct API requested) |

No hand-written tile markers or protocol barriers in the main loop; the one hand barrier is a real
epilogue synchronization and is visible to the verifier. The library's own `tile/` modules contain
the expected low-level address/instruction generation (`fmha_swz`, `RowsCopy`, `Frag` layouts), as
they are the abstraction implementation, not kernel code.

## 3. Safety: generated contracts/markers vs hand, and attacks

`crates/amdgpu-compiler/tests/dsl_tile_audit.rs` (3/3 pass):

| DSL kernel | DSL: errors / ledger / contracts | hand: errors / ledger / contracts | tile proof |
|---|---|---|---|
| `dsl_vs128` | 0 / 6 assume_trusted / 29 | 0 / 6 / 29 | DSL `tile-reads 58880`, `tile-cover 600` (hand: no tile markers) |
| `dsl_t128` | 0 / 4 / 29 | 0 / 4 / 29 | DSL `tile-reads 29440`, `tile-cover 336` |
| `dsl_kvsplit` | 0 / 12 / 36 | 0 / 12 / 36 | DSL `tile-reads 240640`, `tile-cover 760` |
| `dsl_combine8h` | 0 / 2 / 6 | 0 / 2 / 6 | neither has tile markers (global bounds only) |

The DSL port has **the same trusted-assume count and the same contract set as the hand kernels** (no
new trust escapes), the same LDS/global proven counts, and adds tile-lifetime markers/proofs where
the hand kernels had none. `--shipped --strict` on the legacy set remains 0 errors/0 warnings.

**Adversarial checks:** (a) a `Tensor` declaration with an overridden **lying allocation** (64 B while
indexing row 7) is rejected `GV-GLB-OOB` (`address [7*ka(0x70)] vs limit [64,64]`); (b) mutating all
160 auto-generated `TileConsume` generations in `dsl_vs128` by +1 gives **53,760 errors**
(`GV-TILE-STALE`/`GV-PROTO-STALE-GEN`) — the verifier catches wrong generations even when the markers
are library-generated; (c) the contract comparison test above would fail on any extra/removed contract
or trust entry.

## 4. Findings and recommendations

1. **Gate: PASS overall; only `_t128` B2H8S2048 is INFO(FAIL) at 0.9692x shipped (-3.08%)** — within
   layout noise of the other rows but outside the 3% target; if the target is strict, this shape needs
   a look (not a correctness issue).
2. **Abstractions are real, not asm wrappers:** 501 lines for four kernels, no markers/waits/barriers
   in the main loops, one hand barrier in the kvsplit epilogue; the remaining hand spots are the
   tables above (contracts, prologue constants, epilogue pointers, combine launch mapping).
3. **Safety is not weaker:** same trusted/contract counts, same LDS/global proofs, new tile proofs;
   lying allocation and wrong generation are rejected.
4. **Residual risks:** the manual split/combine contracts (lines 77-89) are still hand-host-truth and
   should be covered by `contract_host_truth` for the DSL set; the manual prologue/epilogue addresses
   are covered by `gpu-verify --strict` but not by a library-level address abstraction; only one
   blocking perf row is borderline.

**Bottom line:** the port is a genuine abstraction-level rewrite with gate parity (OVERALL PASS,
correctness/accuracy/determinism/stress all PASS, five blocking perf rows PASS, one informational
row -3.08%), and the automatically generated contracts/markers are at least as strong as the hand
kernel's. No new soundness hole was found.
